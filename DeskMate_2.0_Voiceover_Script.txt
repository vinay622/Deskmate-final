SECTION 1: OPENING — INTRODUCE DESKMATE  (~1 min)
────────────────────────────────────────────────────────────────────────────────

Hello everyone. Today I'm walking you through DeskMate 2.0 — an AI-powered
helpdesk assistant I built for college students.

The problem is simple: students waste hours hunting for basic information.
They call offices that don't pick up, walk to the wrong department, or dig
through 40-page PDFs buried deep on the college website.

DeskMate lets a student type a question in plain language — "What is the
hostel fee for second-year B.Tech students?" — and get an accurate, cited
answer in seconds, 24/7.

Crucially, DeskMate doesn't guess. Every answer comes from documents that
the college administration has officially uploaded. If the information
hasn't been uploaded, it either says so or routes the student to the right
staff member.

There are two user roles: students use the chat interface; administrators
manage the knowledge base, staff directory, announcements, and analytics.

What makes this different from a basic chatbot? Three things. First, it uses
Retrieval-Augmented Generation — retrieving real documents before generating
answers. Second, it's an AI agent that classifies intent, detects language,
personalizes answers, and auto-creates support tickets. Third, it has
complete college-scoped data isolation — colleges on the same platform
never see each other's data.

Let's see it in action.

SECTION 6: AI / INTELLIGENT FEATURES  (~2 min)
────────────────────────────────────────────────────────────────────────────────

Let me explain what happens behind the scenes when a student sends a query.

First, intent analysis. A two-tier system: fast regex catches obvious
greetings, courtesies, and off-topic queries — zero API calls, zero cost.
For ambiguous queries, Gemini classifies the intent and detects the language
— English, Hindi, Telugu, Tamil, and more. Only genuine college queries
enter the full RAG pipeline.

RAG — Retrieval-Augmented Generation — is the heart of DeskMate. Think of
an open-book exam: you look up the relevant pages first, then write your
answer using that information. That's exactly what RAG does.

The step-by-step process:
  1. The query is embedded into a 1024-dimensional vector using Pinecone's
     multilingual-e5-large model.
  2. The semantic cache is checked — if a 98%+ similar query was already
     answered, that cached answer returns instantly (~200ms vs ~3 seconds).
  3. On a cache miss, Pinecone is searched for the top 30 similar document
     chunks.
  4. Chunks from expired or failed documents are filtered out; top 5 kept.
  5. A system prompt is built with the AI's rules, the student's profile,
     the 5 context chunks, conversation history, and the question.
  6. Google Gemini streams the response token by token to the browser.
  7. After generation, the answer is cached and the query is logged for
     analytics.

This ensures every answer is accurate, fast, cited, and traceable.


────────────────────────────────────────────────────────────────────────────────
SECTION 7: DOCUMENT UPLOAD AND KNOWLEDGE BASE  (~1 min 30 sec)
────────────────────────────────────────────────────────────────────────────────

Switching to the admin side. On the Documents page, admins see all uploaded
documents with names, categories, processing status, and expiry dates.

Clicking "Add Document" offers two options: upload a file (PDF, DOCX, TXT,
or image) via drag-and-drop, or sync a URL using Firecrawl.

The processing pipeline behind a file upload:
  1. File goes to Supabase Storage; metadata is saved with status
     "processing."
  2. Text is extracted — mammoth for DOCX, built-in parsing for PDFs, OCR
     for images.
  3. Text is split into ~1,000-character chunks with 200-character overlap
     to preserve context at boundaries.
  4. Each chunk becomes a 1,024-dimensional embedding, processed in batches
     of 10.
  5. Vectors with metadata are upserted into Pinecone in batches of 100.
  6. Status updates to "ready" (or "failed" for retry).

For URL sync, Firecrawl scrapes the page — handling JavaScript, popups,
and cookie banners — returns clean Markdown, and the same chunk-embed-store
pipeline runs.


────────────────────────────────────────────────────────────────────────────────
SECTION 8: DATABASE ARCHITECTURE  (~45 sec)
────────────────────────────────────────────────────────────────────────────────

DeskMate uses two complementary storage systems.

Supabase PostgreSQL is the relational database — it stores users, profiles,
chat sessions, messages, document metadata, staff directory, tickets,
announcements, query logs, and admin codes. Ten core tables, all with Row
Level Security policies.

Pinecone is the vector database — it stores document chunk embeddings for
semantic search (main namespace) and query-answer pairs for semantic caching
(separate "semantic_cache" namespace).

The database handles application logic; Pinecone handles semantic
intelligence. They're complementary, not competing.

SECTION 10: BACKEND ARCHITECTURE  (~1 min)
────────────────────────────────────────────────────────────────────────────────

The backend follows a clean four-layer structure.

Layer 1 — Client: the browser, with Astro-rendered UI and minimal
JavaScript. Layer 2 — Server: TypeScript API routes running as serverless
functions on Vercel, with middleware enforcing auth and RBAC on every
request. Layer 3 — Data Storage: Supabase PostgreSQL for structured data,
Supabase Storage for files, Pinecone for vectors and caching. Layer 4 —
External APIs: Google Gemini for language generation and function calling,
Pinecone Inference for embeddings, Firecrawl for web scraping.

The system uses a fail-closed security model — if any authorization check
fails, access is denied, never defaulted. This prevents unauthorized data
from ever reaching the AI.

================================================================================
               PART 3 — TECHNICAL ARCHITECTURE EXPLANATION
================================================================================

(Use this when a judge asks: "Can you explain what happens behind the scenes?")

--------

Absolutely. The architecture has four layers.

At the top, the Client layer — the browser. Students and admins interact with
an Astro-rendered UI that ships minimal JavaScript for fast performance.

Second, the Server layer. All business logic runs as TypeScript API routes
inside Astro, deployed as serverless functions on Vercel. Every request passes
through a middleware that validates the session using Supabase Auth, fetches
the user's profile and role, and enforces access control before anything else
runs.

Third, the Data layer. There are three storage systems working together.
Supabase PostgreSQL is the primary relational database — it stores user
accounts, profiles, chat sessions, messages, document metadata, staff
directory, escalation tickets, announcements, query logs, and admin access
codes. Every table has Row Level Security policies for college-scoped data
isolation. Supabase Storage holds the actual uploaded files. And Pinecone,
the vector database, stores two things: document chunk embeddings for
semantic search, and a semantic cache of previous query-answer pairs.

Fourth, External APIs. Google Gemini handles natural language generation,
intent classification, and agentic function calling. Pinecone Inference
generates 1024-dimensional vector embeddings using the multilingual-e5-large
model. And Firecrawl handles web scraping for URL-based document ingestion.

The complete flow when a student asks a question is: the browser sends a
POST to /api/chat/generate. The server rate-limits by checking query_logs
in Supabase. Intent analysis runs — first with fast regex patterns, then
with Gemini for ambiguous queries. If it's a genuine college question, the
query is embedded, the semantic cache is checked, and on a cache miss, the
top 30 similar chunks are retrieved from Pinecone, filtered against Supabase
to remove expired documents, reduced to the top 5, and packed into a system
prompt along with the student's profile and conversation history. Gemini
streams back the response token-by-token directly to the browser. In the
background, the response is cached for future similar queries, and the
entire interaction is logged for analytics.

The document ingestion pipeline works similarly: file upload to Supabase
Storage, text extraction using mammoth for DOCX or native parsing for
other formats, chunking into ~1000-character overlapping segments, batch
embedding via Pinecone Inference, and batch upsert to the Pinecone index
with metadata. For URLs, Firecrawl scrapes the page first, then the same
chunk-embed-store pipeline runs.

The system uses a fail-closed security model — if any authorization check
fails, access is denied rather than defaulted. RLS policies, server-side
middleware, admin access codes, student approval workflows, and
college-scoped data filtering all work together to ensure comprehensive
security.

               PART 4 — 30-SECOND PROJECT SUMMARY
================================================================================

(Use this when someone asks: "What is your project?")

--------

DeskMate 2.0 is an AI-powered helpdesk for college students. Students type
a question — in English, Hindi, or Telugu — and DeskMate searches through
the college's officially uploaded documents, finds the relevant information,
and generates a precise, cited answer using Google Gemini and a
Retrieval-Augmented Generation pipeline. It's not a generic chatbot — it
only answers from verified documents, personalizes responses based on the
student's profile, and automatically routes to human staff when it can't
help. For admins, there's a full dashboard to manage documents, staff,
students, announcements, tickets, and analytics. The entire system uses
Astro for the frontend, Supabase for the database and auth, Pinecone for
vector search and semantic caching, and deploys on Vercel. It's a
complete, production-grade AI platform — not just a CRUD application.
