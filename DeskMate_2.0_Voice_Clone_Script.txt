SECTION 6: AI / INTELLIGENT FEATURES  (~2 min)
────────────────────────────────────────────────────────────────────────────────

Okay, so this is where it gets *really* interesting. Let me explain what's
actually happening behind the scenes when a student sends a question.

First up — intent analysis. [pause] DeskMate doesn't just blindly throw
every message at the AI. It uses a two-tier classification system.

Tier one is super fast regex-based pattern matching. Simple greetings like
"Hi" or "Hello"? Caught instantly — zero API calls, zero cost, zero
latency. Same for "Thanks" or "Bye," and off-topic stuff like "Write me a
Python script." All handled without touching the expensive AI pipeline.

For trickier queries, tier two kicks in — Gemini itself classifies the
intent and detects the language. English, Hindi, Telugu, Tamil, Kannada,
you name it.

Only genuine college queries make it to the full RAG pipeline.

So — what *is* RAG? [pause] RAG stands for Retrieval-Augmented Generation,
and honestly, this is the *heart and soul* of DeskMate.

Think of it like an open-book exam, right? You don't answer from memory
alone — you look up the relevant pages first, read the specific paragraphs,
and *then* write your answer. That's exactly what RAG does.

Here's the step-by-step flow:

Step one — the student's question gets converted into a 1024-dimensional
vector embedding using Pinecone's multilingual-e5-large model. Basically,
it turns the text into math that the computer can compare.

Step two — before doing anything expensive, we check the semantic cache.
If someone recently asked a nearly identical question — like 98% similarity
or higher — the cached answer comes back *instantly*. We're talking 200
milliseconds instead of three seconds. Huge difference!

Step three — if it's a cache miss, the embedding searches Pinecone for the
top 30 most similar document chunks.

Step four — those chunks get filtered against Supabase to remove anything
from expired or failed documents. Only the top 5 survive.

Step five — a detailed system prompt is built with the AI's behavioral
rules, the student's profile info, those 5 context chunks, conversation
history, and the actual question.

Step six — this goes to Google Gemini, which streams back the response
token by token.

And step seven — after generation, the answer gets cached for future
similar questions, and the whole interaction is logged for analytics.

So basically, every single answer is accurate, fast, cited, and fully
traceable. [pause] I think that's *really* powerful.

────────────────────────────────────────────────────────────────────────────────

Alright, let's switch over to the admin side now! [pause] Because the

On the Documents page, admins can see all uploaded documents with names,

Clicking "Add Document" gives you two options — upload a file via drag-and-
drop — PDF, DOCX, TXT, or even images — *or* sync a URL using our
Firecrawl integration. Let me walk through a file upload.

Now, here's what happens behind the scenes — and this is one of my
*favorite* parts of the project:

First, the file goes to Supabase Storage and a metadata record is created
with status "processing."

Then, text extraction. For PDFs, built-in parsing. For Word documents, a
library called mammoth converts them to text. Images? OCR-based extraction.

Next — chunking! The text gets split into roughly 1,000-character chunks
with a 200-character overlap. Why the overlap? Because sentences can get
cut at chunk boundaries, and the overlap ensures important info is captured
in at least one chunk completely.

Then each chunk gets turned into a 1,024-dimensional embedding — processed
in batches of 10 to stay within rate limits.

And finally, all those vectors with metadata get upserted into Pinecone in
batches of 100. Once done, the document status flips to "ready." If
anything goes wrong, it's marked "failed" so the admin can retry.

For the URL sync option — super convenient! Admin just pastes a URL,
Firecrawl goes out and scrapes the page — handles JavaScript rendering,
cookie banners, popups, everything — and returns clean Markdown. Then the
same chunk-embed-store pipeline kicks in.

Pretty seamless, right?

SECTION 8: DATABASE ARCHITECTURE  (~45 sec)
────────────────────────────────────────────────────────────────────────────────

Okay, quick but important distinction here. [pause] DeskMate uses *two*
very different storage systems, and understanding why both exist is key.

Supabase PostgreSQL is the relational database — it handles all structured
application data. Users, profiles, chat sessions, messages, document
metadata, staff directory, tickets, announcements, query logs, admin codes.
Ten core tables, every single one with Row Level Security policies.

Then there's Pinecone — the vector database. This doesn't store user data
at all. It stores vectorized document knowledge in two namespaces: the main
one for document chunk embeddings, and a separate "semantic_cache" one for
query-answer pairs.

So basically — Supabase handles the *application logic*, Pinecone handles
the *semantic intelligence*. They're complementary, not competing. Both
essential!

SECTION 10: BACKEND ARCHITECTURE  (~1 min)
────────────────────────────────────────────────────────────────────────────────

Alright, let me quickly walk you through the overall backend architecture.
[pause] It follows a clean four-layer structure.

Layer 1 — the Client. That's the browser. Astro-rendered UI, minimal
JavaScript. Fast and lightweight.

Layer 2 — the Server. TypeScript API routes running as serverless functions
on Vercel. Every single request goes through the Astro middleware first —
session validation, role checking, access control. No shortcuts.

Layer 3 — Data Storage. Three systems working together: Supabase PostgreSQL
for structured data, Supabase Storage for uploaded files, and Pinecone for
vectors and semantic caching.

Layer 4 — External APIs. Google Gemini for language generation and function
calling. Pinecone Inference for embeddings. Firecrawl for web scraping.

And here's something I want to emphasize — the system uses a *fail-closed*
security model. If any authorization check fails — network error, timeout,
whatever — access is *denied*, never defaulted. So unauthorized data can
never accidentally reach the AI. That's a really important design decision.

SECTION 12: SECURITY  (~45 sec)
────────────────────────────────────────────────────────────────────────────────

Alright, security — really important, so let me hit the highlights quickly.
[pause]

Row Level Security on *every* single table. Even if someone bypasses the
app code and queries Supabase directly, they can only see what they're
authorized to see.

Server-side role-based access control via middleware — not client-side
hiding.

One-time admin access codes tied to specific colleges. Student approval
workflow — pending until the admin says yes.

Database-backed rate limiting — 20 queries per user per minute, and it
persists across server restarts so you can't just reconnect to bypass it.

Fail-closed authorization — if a check fails, access is *denied*, period.

Automatic document expiration enforcement — even if vectors exist in
Pinecone, expired documents get filtered out before reaching the AI.

College-scoped data isolation across *all* queries. And session auth via
HTTP-only cookies validated server-side.

Security is baked into *every layer* of this system.

================================================================================
               PART 3 — TECHNICAL ARCHITECTURE EXPLANATION
================================================================================

(Use this when a judge asks: "Can you explain what happens behind the scenes?")

--------

Oh absolutely, great question! So the architecture has four layers —
let me walk you through each one.

At the top, the Client layer — that's the browser. Students and admins
interact with an Astro-rendered UI that ships *minimal* JavaScript, which
keeps everything super fast.

Second, the Server layer. All business logic runs as TypeScript API routes
inside Astro, deployed as serverless functions on Vercel. And here's the
key — every single request passes through a middleware that validates the
session using Supabase Auth, fetches the user's profile and role, and
enforces access control *before* anything else runs.

Third, the Data layer. Three storage systems working together. Supabase
PostgreSQL is the primary relational database — it handles user accounts,
profiles, chat sessions, messages, document metadata, staff directory,
escalation tickets, announcements, query logs, and admin access codes.
Every table has Row Level Security policies. Supabase Storage holds the
uploaded files. And Pinecone — the vector database — stores document chunk
embeddings for semantic search, plus a semantic cache of past query-answer
pairs.

Fourth, External APIs. Google Gemini handles language generation, intent
classification, and agentic function calling. Pinecone Inference generates
1024-dimensional embeddings. And Firecrawl handles web scraping for URL
ingestion.

Now the complete flow when a student asks a question — this is the fun
part! The browser sends a POST to /api/chat/generate. Rate limiting checks
query_logs in Supabase. Intent analysis runs — fast regex first, then
Gemini for ambiguous cases. If it's a genuine college question, the query
gets embedded, semantic cache is checked, and on a miss, top 30 chunks
come from Pinecone, get filtered against Supabase for expired docs, reduced
to top 5, and packed into a prompt with the student's profile and chat
history. Gemini streams the response directly to the browser. Background
caching happens, and everything gets logged for analytics.

The document pipeline is similar — upload to Supabase Storage, extract
text, chunk into overlapping segments, batch embed, batch upsert to
Pinecone. For URLs, Firecrawl scrapes first, then the same pipeline runs.

And the whole thing uses a fail-closed security model — if any check fails,
access is denied, never defaulted. RLS, middleware, access codes, approval
workflows, and college-scoped filtering all work together. Really robust!
